## 摘要

本项目是一款以北京大学信息科学技术学院大一课程为背景的**乙女向养成模拟游戏**。玩家扮演的信科女生因期末通宵晕倒穿越至异世界，与四门拟人化课程（**程序设计、高等数学、线性代数、人工智能引论**）共度一学期。通过 5 周剧情推进、4 门学科好感度培养、5 款知识小游戏训练、三组数值管理（好感度 / 压力 / 黑化），玩家的选择将触发**五种迥异的结局**——包括默认结局、挚爱结局、告别结局、黑化结局与压力结局。

### 项目关键指标

| 维度 | 数值 |
|---|---|
| 源代码规模 | **~6400 行** C++ / 44 个 `.cpp` + `.h` 文件 |
| 剧本资产 | 14 个 JSON 文件 · **237 节点** · 0 断链 / 0 孤儿 / 0 死端 |
| 小游戏 | **5 款** 独立类，均派生自 MiniGame 抽象基类 |
| 结局设计 | **5 种**，由 EndingJudge 按优先级链判定 |
| 美术资源 | 4 角色立绘 · 5 场景背景 · 主菜单背景 · UI 图标 |
| 自动化测试 | 30 个用例，100% PASS |
| 编译验证 | Qt 6.11 · CMake · macOS 编译通过（三平台 CI 支持）|
| 开发周期 | 2026-05-13 立项 → 2026-06-06 初版提交 · 约 4 周 |

### 五个技术亮点

1. **OOP 多态 + 工厂模式**：`Subject` / `MiniGame` 抽象基类，通过基类指针驱动派生行为
2. **单例 + RAII**：`GameManager` 全局唯一实例，`Player` 用智能指针管理动态对象
3. **信号槽解耦**：数值变化 → UI 自动刷新，小游戏结束 → GameManager 统一奖惩
4. **数据驱动**：剧本、题库均为外置 JSON，非程序员可独立编辑；引擎内实现了完整的 condition 表达式求值器
5. **CMake 跨平台 + GitHub Actions CI**：一份配置在 macOS / Windows / Linux 三平台编译

## 第 1 章 项目背景与设计目标

### 1.1 立项动机

北大信科大一课程节奏紧凑、难度陡峭——程序设计、高等数学、线性代数、人工智能引论四门核心课程构成新生的主要负担。本项目将**这四门课拟人化为四位性格迥异的角色**，让玩家在游戏叙事中"重新经历"一个学期，把学术压力转化为情感体验。这既是致敬也是自嘲。

### 1.2 玩法定位

- **主题类型**：乙女向养成模拟（Otome / SLG）
- **玩家操作**：每日时段选择、剧情选项、小游戏挑战、最终抉择
- **可玩时长**：单条路径约 30–60 分钟；5 结局全收集约 3 小时
- **心智模型**：管理三组数值（好感 × 4 / 压力 / 黑化），触发不同角色路线

### 1.3 四位学科角色

| 角色 | 性格关键词 | 语言风格样例 | 特殊机制 |
|---|---|---|---|
| **程设 ProgDesign** | 理性、克制、务实 | "工具的价值，是看它在谁手上" | 关联扫雷（主）+ 21 点 |
| **高数 Calculus** | 神秘、抽象、爱哲学 | "趋近，但永不到达——的爱情" | 关联 21 点（教学扑克类） |
| **线代 LinearAlgebra** | 阴郁、观察、系统强迫症 | "你不会从我的坐标系里出去" | 关联**记忆翻牌**；含 **darkness 黑化机制** |
| **AI 引论 AIIntro** | 酷感、未来感 | "学习本质上是反向传播" | 关联井字棋（主）+ AI 迷宫 |

**特别说明**：线代的「好感度」在设定上记录的是**她对玩家的观察深度**，这是 End4「永远的线代」结局的叙事根基。

### 1.4 玩家的六个操作维度

1. **每日时段选择**：上课 / 翘课 / 自习 / 出游
2. **对话选项**：每个剧情节点 2–3 个选项，影响好感与黑化
3. **小游戏挑战**：由角色发起，胜负决定数值奖惩
4. **主攻学科选择**：第 3 周（期中）显式选择，决定中期支线走向
5. **信物接收**：第 4 周好感 ≥ 50 才可领取，是结局判定的关键凭证
6. **最终选择**：第 5 周结束时决定回现实 / 留下 / 被锁定

### 2.3 场景切换有限状态机

游戏在 5 个主场景之间切换，全部通过 `QStackedWidget` 管理：

```
     MainMenu ──开始/继续──> Map ──点击热区──> Dialog ──特定节点──> MiniGame
        ↑                    ↑                    ↓                    ↓
        │                    │                    │              MiniGame::finished
        │                    └────Dialog::scriptFinished─────────────┘
        │                                         │
        └────────────结束──────Ending<─────结局触发┘
```

由 `GameManager::requestScene(GameScene::X)` 统一触发切换，任何模块只需 `connect` 一个 signal。

### 2.4 数据流：一次完整的"选项 → 数值 → UI 刷新"

以玩家在剧本里选"我准备好了"（effects: stress+3, affinity.ProgDesign+2）为例：

```
1. DialogWindow 检测到玩家点击选项按钮
   ↓ emit choiceSelected(idx)
2. StoryEngine::onChoiceSelected 解析该 choice 的 effects 数组
   ↓ 对每个 effect 调用 player_->addStress(+3), addAffinity(+2)
3. Player 内部数值 clamp 到 [0, 100]，emit stressChanged(newValue)
   ↓
4. StatusBar 的 slot::onStressChanged 收到，更新进度条 UI
5. StoryEngine 跳转到 choice.next 节点，emit nodeChanged()
   ↓
6. DialogWindow 读取当前节点，刷新台词 + 选项按钮
```

**关键**：每一步都通过信号槽解耦，任何组件都可以独立测试 / 替换。

### 3.2 数据驱动的剧本格式

每个剧本文件是一个 JSON，结构如下：

```json
{
  "title": "第一周·穿越异世界",
  "startNode": "intro_01",
  "nodes": [
    {
      "id": "intro_01",
      "speaker": "ProgDesign",
      "text": "终于醒了？我是程序设计……",
      "choices": [
        {
          "text": "请多关照",
          "next": "intro_02",
          "effects": [{"target": "affinity.ProgDesign", "delta": 2}],
          "condition": "darkness < 30"
        }
      ]
    }
  ]
}
```

**字段说明**：

| 字段 | 说明 |
|---|---|
| `id` | 节点唯一标识 |
| `speaker` | `narrator` / `player` / 四角色名 |
| `text` | 显示台词，`\n` 换行 |
| `choices` | 选项数组；引擎里对空 choices 有明确的死锁检测 |
| `condition` | 可选，节点级为"硬门"（不满足直接结束）、选项级为"软门"（仅隐藏该选项）|
| `effects.target` | `affinity.<X>` / `stress` / `darkness` |
| `effects.delta` | 整数，自动夹紧到 `[0, 100]` |
| `next: "END"` | 触发 `scriptFinished` 信号 |

### 3.3 Condition 表达式引擎

引擎实现于 [`StoryEngine.cpp:227-294`](../src/story/StoryEngine.cpp)，采用**递归字符串拆分**的最小实现，无需引入表达式解析库：

```
原子：  <变量> <运算符> <数字>
        例: "affinity.LinearAlgebra >= 50"
组合：  原子 && 原子 && ...      （全为真）
        原子 || 原子 || ...      （任一为真）
变量：  affinity.{ProgDesign,Calculus,LinearAlgebra,AIIntro},
        stress, darkness, week, day
运算符：> >= < <= == !=
优先级：||  >  &&  >  atomic
```

代码结构：

```cpp
bool StoryEngine::evaluateCondition(const QString& expr) const {
    if (expr.contains("||")) {
        for (auto& p : expr.split("||"))
            if (evaluateCondition(p)) return true;
        return false;
    }
    if (expr.contains("&&")) {
        for (auto& p : expr.split("&&"))
            if (!evaluateCondition(p)) return false;
        return true;
    }
    return evaluateAtomic(expr);  // 正则匹配变量-运算符-数字
}
```

### 3.5 三个关键设计决策

#### 3.5.1 Hub 节点 + condition 分流（角色支线对话池）

每个 route 文件用一个 **hub 节点**做 `startNode`，choices 全为同一句「（继续）」但带不同 `condition`，实现按玩家状态的隐式分发：

```json
{
  "id": "calculus_hub",
  "speaker": "narrator",
  "text": "（你走向高数的座位）",
  "choices": [
    {"text": "（继续）", "next": "calculus_lv1",       "condition": "affinity.Calculus < 50"},
    {"text": "（继续）", "next": "calculus_lv2_phil",  "condition": "affinity.Calculus >= 50 && affinity.Calculus < 80"},
    {"text": "（继续）", "next": "calculus_endgame",   "condition": "affinity.Calculus >= 80"}
  ]
}
```

`currentChoices()` 会过滤 condition 不满足的选项，同一时刻只有一个按钮可见，玩家视觉上就是一次"继续"，实际已按当前状态被分发到对应阶段。**全部分发逻辑由剧本条件表达式承载，不涉及 C++**。

#### 3.5.2 线代黑化值的多档次台词

同一节点提供两套互斥台词，让**相同场景在不同状态下语义完全不同**：

```json
{
  "id": "w3_la_3",
  "choices": [
    {"text": "（背脊发凉）",       "condition": "darkness < 30",  "effects": [...]},
    {"text": "（你居然觉得动人）", "condition": "darkness >= 30", "effects": [...]}
  ]
}
```

低黑化玩家读这句台词会"背脊发凉"压力 +3；高黑化玩家则会"觉得动人"，黑化再 +5。**同一句台词承载两条情感曲线**——这是数据驱动让剧本设计弹性最大化的样例。

#### 3.5.3 线代的观察者语法

线代的台词体系专注于**监控与归档的描述**。所有台词遵循三条语法规则：

1. 主语很少是"我对你 …"，多为对系统/状态的陈述
2. 数字与精度词汇（时间、次数、坐标）高频出现
3. 物理动作由器物代偿（钳子、腕表、项链、小本子）

具体台词范例：

| 场景 | 台词 |
|---|---|
| week1 初见 | "我能感知到你的位置。我们之间——有连续的映射。" |
| week2 午饭 | "这是你这两周吃过的所有东西。你比你以为的有规律。" |
| week3 长夜 | "我要完整的视野，手机放我这里。" |
| week4 项链 | "这个扣是我特地改的，自己拿不下来。你不会从我的坐标系里失踪。" |
| week5 告白 | "这五周你出现在我视野里 3892 次。这个数字下周一之后不会再涨。" |
| End4 结局 | "你不会从我的坐标系里出去。这一次——是永远。" |

她的高好感等价于「玩家未能逃出她的观察系统」，End4 的触发因此叙事完整：**系统终于把变量锁定**。

### 3.6 结局判定优先级链

由 `EndingJudge` 按下面的优先级判定，实现于 [`EndingJudge.cpp`](../src/story/EndingJudge.cpp)：

```cpp
// 优先级从高到低（先满足者胜出）
1. stress >= 100          →  End5「陌生的天花板」
2. darkness >= 100        →  End4「永远的线代」
3. max(affinity) >= 80
     choseToStay == true  →  End2「Best Love」
     choseToStay == false →  End3「再见」
4. 上述均不满足           →  End1「3.92」（默认）
```

**关键立意**：End5 优先级最高——把玩家健康放在爱情之上。这是本作在游戏内外都想表达的立场。

### 4.3 主窗口与场景切换

`MainWindow` 内含一个 `QStackedWidget`，五个场景 widget 作为其子页：

```cpp
enum class GameScene { MainMenu, Map, Dialog, MiniGame, Ending };

connect(&GameManager::instance(), &GameManager::sceneChangeRequested,
        this, &MainWindow::onSceneRequested);

void MainWindow::onSceneRequested(GameScene s) {
    stackedWidget_->setCurrentIndex(static_cast<int>(s));
}
```

**优点**：任何模块想切换场景，只需 `GameManager::instance().requestScene(...)`，完全不需要持有 MainWindow 指针。

MainWindow 还提供了**数值调试菜单**（顶栏 Debug 菜单），可以直接修改玩家数值以测试各条剧情线——便于三人协作时手动验证 5 结局的触发。

### 4.4 状态栏与信号槽联动

状态栏实时显示所有关键数值。**关键设计**：状态栏不直接读 Player，而是订阅 Player 的 `valueChanged` 信号：

```cpp
connect(player, &Player::affinityChanged, this, &StatusBar::onAffinityChanged);
connect(player, &Player::stressChanged,   this, &StatusBar::onStressChanged);
connect(player, &Player::darknessChanged, this, &StatusBar::onDarknessChanged);
connect(player, &Player::dateChanged,     this, &StatusBar::onDateChanged);
```

**收益**：任何数值变化都会自动反映到 UI，无需在每次修改数值处显式调用刷新方法。

**状态栏 UI 布局**：4 个 QProgressBar 用 QGridLayout 排 2×2（好感度），另外两个 QProgressBar 独立显示压力 / 黑化，最左侧一个 QLabel 显示"第 X 周 · 第 Y 天"。

## 第 5 章 玩法系统实现（沈昱萱 · `src/core/` + `src/games/`）

### 5.1 模块概览

玩法系统包含核心调度层（`src/core/`，**694 行**）和小游戏层（`src/games/`，**3243 行**），是全项目最大的代码模块：

| 文件 | 职责 |
|---|---|
| `Player.{h,cpp}` | 数值封装 + signals，clamp 到 `[0, 100]` |
| `GameManager.{h,cpp}` | 单例调度器 + 场景切换 + 数值奖惩派发 |
| `SaveManager.{h,cpp}` | JSON 序列化多存档槽，写入用户 AppData 目录 |

5 个小游戏均继承自 `MiniGame` 抽象基类，通过统一的 `finished(int score, bool won)` signal 回传结果。

### 5.2 Player：数值封装与信号广播

```cpp
class Player : public QObject {
    Q_OBJECT
public:
    void addAffinity(SubjectType s, int delta);
    void addStress(int delta);
    void addDarkness(int delta);
    void advanceDay();
    void useFreeDay();  // 消耗一个"自由日"跳过剧情
    // getters: affinity(), stress(), darkness(),
    //          currentWeek(), currentDay(), freeDaysLeft()

signals:
    void affinityChanged(SubjectType s, int newValue);
    void stressChanged(int newValue);
    void darknessChanged(int newValue);
    void dateChanged(int week, int day);

private:
    std::array<int, 4> affinity_{0, 0, 0, 0};
    int stress_ = 0, darkness_ = 0;
    int week_ = 1, day_ = 1;
    int freeDaysLeft_ = 3;  // 每周 3 个自由日
};
```

**关键设计**：
- 所有数值 setter 内部会 `clamp` 到 `[0, 100]`，然后 emit 对应 signal
- 调用方**不需要关心数值边界**——超出无效，UI 自动刷新
- `freeDaysLeft` 是一周自由日额度，玩家可以用它跳过某些剧情节点直接推进日期

### 5.3 GameManager：单例调度器

单例模式实现：

```cpp
GameManager& GameManager::instance() {
    static GameManager s_instance;
    return s_instance;
}
```

**职责**：
1. 持有 Player 与 4 个 Subject 对象
2. 处理场景切换请求
3. 监听所有 MiniGame 的 `finished` 信号，统一按学科关系应用奖惩规则
4. 触发 SaveManager 存档
5. 游戏结束时调用 EndingJudge 判定结局

**小游戏奖惩派发**（`onMiniGameFinished` 核心逻辑）：

```cpp
void GameManager::onMiniGameFinished(MiniGameType type, int score, bool won) {
    switch (type) {
        case MiniGameType::Minesweeper:            // 扫雷 → 程设
            if (won) { addAffinity(ProgDesign, +10); addStress(+5); }
            else     { addStress(+15); }
            break;
        case MiniGameType::MemoryMatch:            // 记忆翻牌 → 线代
            if (won) { addAffinity(LinearAlgebra, +10); addStress(+5); }
            else     { addStress(+15); }
            break;
        case MiniGameType::TicTacToe:              // 井字棋 → AI 引论
            if (won) { addAffinity(AIIntro, +10); addStress(+5); }
            else     { addStress(+15); }
            break;
        // ... 其余类似
    }
}
```

**统一的奖惩哲学**：胜利均为 **+10 好感 / +5 压力**（学习状态）；失败均为 **+15 压力**，**不扣好感**（鼓励参与）。这种统一映射让新增小游戏时无需修改主控。

### 5.4 SaveManager：多存档槽

支持 3 个存档槽，全部序列化为 JSON 存于 `QStandardPaths::AppDataLocation`：

```
macOS: ~/Library/Application Support/StudyAdventure/save_1.json
Linux: ~/.local/share/StudyAdventure/save_1.json
Windows: %APPDATA%/StudyAdventure/save_1.json
```

**存档格式**：

```json
{
  "slot": 1,
  "timestamp": "2026-05-31T21:44:00",
  "player": {
    "stress": 40,
    "darkness": 15,
    "week": 3,
    "day": 5,
    "freeDaysLeft": 2,
    "affinity": {
      "ProgDesign": 45, "Calculus": 30,
      "LinearAlgebra": 20, "AIIntro": 60
    }
  },
  "completedScripts": ["week1.json", "week2.json"],
  "currentScene": "Map",
  "currentScriptPath": ":/scripts/week3.json",
  "currentNodeId": "w3_after_exam"
}
```

**读档流程**：
1. `SaveManager::load(slot)` 读 JSON
2. 恢复 Player 数值（触发所有 `valueChanged` signal → 状态栏刷新）
3. `StoryEngine::loadScript(path)` + `jumpToNode(nodeId)` 恢复剧本进度
4. `GameManager::requestScene(currentScene)` 切回原场景

### 5.5 五个小游戏

5 款小游戏全部继承自 `MiniGame` 抽象基类：

```cpp
class MiniGame : public QWidget {
    Q_OBJECT
public:
    virtual void start() = 0;
    virtual void reset() = 0;
    virtual MiniGameType type() const = 0;
    virtual QString displayName() const = 0;
    void setDifficulty(Difficulty d);

signals:
    void finished(int score, bool won);
    void stressOccurred(int delta);
};
```

#### 5.5.1 扫雷 Minesweeper（关联程设）

- 3 难度分级（9×9 / 16×16 / 22×22），高难度需程设好感 ≥ 30 / 60 解锁
- 首次点击保护（第一次不会踩雷）
- 自动展开 0 邻雷区域
- **奖惩**：胜 +10 好感 / +5 压力；败 +15 压力

#### 5.5.2 21 点 Blackjack（关联程设 / 高数）

- A 灵活按 1 或 11 计（取不爆的最大值）
- 庄家固定策略：`< 17 必须要牌，≥ 17 必须停牌`
- Blackjack（初始 21）直接翻倍奖励
- **技术亮点**：呼应程设课程的"扑克类设计"经典作业
- **奖惩**：胜 +10 好感 / +5 压力；败 +15 压力

#### 5.5.3 井字棋 TicTacToe（关联 AI 引论）· 核心亮点

- 3 难度：简单（随机）/ 普通（Minimax）/ 困难（**Minimax + α-β 剪枝**）
- **困难模式 AI 永不输**——AI 引论课程"零和博弈完美信息"经典案例的可视化
- 困难模式平局触发 AI 特殊剧情（AI 会向玩家透露异世界秘密）
- **算法教学意义**：AI 思考时会在棋盘上短暂高亮其搜索过的关键节点，让玩家直观看到 "AI 在想什么"
- **奖惩**：胜 +10 好感 / +5 压力；败 +15 压力；困难平局触发专属剧情

#### 5.5.4 记忆翻牌 MemoryMatch（关联线代）

- 玩家翻开成对的相同图案卡牌，全部匹配后获胜
- 3 难度：4×4 / 6×6 / 8×8 卡牌规模
- 时间 + 翻卡次数双维度评级
- **设计意图**：与线代"空间记忆 / 秩序识别"的隐喻贴合——线代欣赏能识别相同结构的玩家
- **奖惩**：胜 +10 线代好感 / +5 压力；败 +15 压力

#### 5.5.5 AI 迷宫 MazeGame（关联 AI 引论）· 教学演示亮点

- 迷宫由**递归回溯算法**动态生成，保证起点到终点存在通路
- 玩家用方向键在迷宫中寻找终点
- 按 **H 键触发 BFS 可视化**：从当前位置到终点的最短路径以渐变色高亮显示
- 3 提示限额，每次持续 2 秒
- 迷宫中有陷阱格和知识格（答题格）
- **S 级评价**：0 提示 + 收集全知识格，AI 好感 +12
- **算法教学意义**：BFS 求最短路径的可视化演示，是 AI 引论中"图搜索"章节的天然教材

### 5.6 六个统一设计哲学

1. **鼓励参与而非惩罚失败**：即使玩家失败，也只加压力不减好感——避免因偶然失误导致剧情线断裂
2. **教育性 + 游戏性并存**：每款游戏映射一个课程知识点
3. **算法可视化教学**：井字棋的 Minimax、AI 迷宫的 BFS 都在 UI 上直接演示
4. **难度渐进解锁**：高难度绑定角色好感门槛，避免"开局劝退"或"后期无事可做"
5. **技术统一性**：全部通过 `MiniGame::finished` signal 回传，主控无需感知具体游戏——**面向对象"对扩展开放、对修改封闭"原则**的体现
6. **数据外置**：题库（如高数题）在 JSON——非程序员可协作扩展

## 第 6 章 五种结局设计

结局由 `EndingJudge` 按优先级链判定。全部 5 结局的剧本文件位于 `assets/scripts/ending_*.json`。

### 6.1 End1「3.92」· 默认结局

> *"这是最常见的结局，也是最体面的告别。"*

**触发**：玩家通关期末考试，任何角色的好感度未达到 80。
**剧本**：7 节点。
**叙事**：玩家回到现实，醒来时桌上是没合上的笔记本。异世界的一切像梦，但笔记里写满了她从未学过、却清晰得不像梦的知识。
**设计立意**：肯定"学习本身的价值"。即使没有任何浪漫落地，玩家依然带回了知识与成长。

### 6.2 End2「Best Love」· 挚爱结局

> *"通道在背后悄然合上。此刻，你已经做出了选择。"*

**触发**：与至少一个角色的好感度 ≥ 80，最终选择"留下"，且黑化 < 60。
**剧本**：7 节点。
**叙事**：异世界边界开始透明，回现实的通道出现。玩家回头看到那个人欲言又止的身影，转身朝 ta 走去。
**设计立意**：这是浪漫线的最终承诺。玩家用现实身份换取此刻的关系。

### 6.3 End3「再见」· 告别结局

> *"你拥有过爱，也选择了责任——这就是成长。"*

**触发**：与至少一个角色的好感度 ≥ 80，但最终选择"回到现实"。
**剧本**：8 节点。
**叙事**：玩家穿过通道，回到现实的桌前。翻开笔记最后一页，看到自己写下的、不像自己字迹的话：

> "程序的本质是表达。"
> "极限的本质是逼近。"
> "线性的本质是叠加。"
> "智能的本质是连接。"

**设计立意**：相较于 End2 的浪漫，End3 颂扬"舍得"。这是**最难选**也是**最成熟**的结局。

### 6.4 End4「永远的线代」· 黑化结局

> *"这里只有我，和你。这是最后的稳态。"*

**触发**：线代黑化值 ≥ 100。优先级仅次于 End5。
**剧本**：5 节点。
**叙事**：玩家醒来时不在任何熟悉的地方——四面墙写满了不断重写自身的方程式。线代说："外面的世界太混乱，所以我把你带到一个只属于我们的子空间里"。
**设计立意**：这是 5 个结局里**最阴森**的。线代台词全部用线性代数概念隐喻——「子空间」、「稳态」、「不变量」——**把数学的冷峻与执着折叠在一起**。

### 6.5 End5「陌生的天花板」· 压力结局

> *"——希望你在现实中，永远不要看到这个画面。好好睡觉，好好吃饭。比分数重要的东西，还有很多。"*

**触发**：玩家压力值 ≥ 100。**优先级最高**。
**剧本**：10 节点（5 个结局中最长）。
**叙事**：玩家在异世界精神崩溃，醒来发现自己在医院——昏迷三天，期末考因病免考。脑中残留四个身影的最后劝告：「学习不是这样学的」「你在用消耗自己的方式换分数」「停下来吧」。
**设计立意**：这是**对游戏内与游戏外都有警示意义**的结局。当玩家把"刷分至上"的习惯延续到游戏里，系统用一个极端结局让玩家看到这种生活方式的终点。**结尾直接对玩家说话，是设计上唯一一次"打破第四面墙"**。

### 6.6 五结局对比

| 结局 | 触发 | 节点 | 情感色调 | 设计立场 |
|---|---|---|---|---|
| End1 「3.92」 | 默认 | 7 | 平静、温暖 | 知识本身值得 |
| End2 「Best Love」 | 高好感 + 留下 | 7 | 浪漫、不舍 | 选择陪伴 |
| End3 「再见」 | 高好感 + 离开 | 8 | 成熟、克制 | 选择责任 |
| End4 「永远的线代」 | 高黑化 | 5 | 阴森、压抑 | 占有的代价 |
| End5 「陌生的天花板」 | 高压力 | 10 | 沉痛、警示 | 健康优先 |

### 8.2 关键技术收获

| 技术点 | 实践形式 |
|---|---|
| **OOP 多态** | Subject / MiniGame 抽象基类 + 派生类，运行时基类指针驱动 |
| **单例模式** | GameManager 全局唯一实例，私有构造 + 静态访问 |
| **信号槽解耦** | 数值 → UI、小游戏结束 → 主控，全部通过 signals 通信 |
| **数据驱动** | JSON 剧本 + JSON 题库 + JSON 存档，代码与内容彻底分离 |
| **状态机 + 表达式引擎** | StoryEngine 递归拆分实现 condition 求值 |
| **智能指针 RAII** | `std::unique_ptr` 管理 Player / Subject 生命周期 |
| **Qt 资源系统** | `.qrc` 打包剧本、题库、图片到二进制内 |
| **CMake 跨平台** | 一份配置三平台编译，Qt 组件自动查找 |
| **Git 协作模型** | develop 主干 + `feature/*` 分支 + PR review |
| **自动化测试** | Python 行为级模拟器 + JSON 结构校验 |

### 8.3 关键工程决策

#### 8.3.1 Route 对话池的 Hub 分流

角色支线的对话池采用 hub 节点方案：每个 route 文件的 `startNode` 是一个空文本的 hub 节点，其 choices 全部是同一句「（继续）」但带不同 condition。分发全部由剧本条件表达式承载，不涉及 C++。

#### 8.3.2 Ending 剧本的显式结束选项

所有结局剧本的终点节点都提供一个「（回到主菜单）」选项，触发 `scriptFinished` 信号让 StoryEngine 回到主菜单场景。

#### 8.3.3 线代人设的观察者语法

线代的全部台词遵循"只描述监控能力、不表达情感诉求"的语法规则。详见 §3.5.3。

#### 8.3.4 小游戏与学科的映射

5 款小游戏覆盖 4 学科：程设关联扫雷（主）和 21 点、高数关联 21 点、线代关联记忆翻牌、AI 引论关联井字棋（主）和 AI 迷宫。

#### 8.3.5 跨模块接口的边界规范

`docs/接口约定.md` §6 明确文件归属：`src/story/` 归剧情、`src/ui/` + `src/map/` 归界面、`src/core/` + `src/games/` 归玩法。跨模块修改需要先在群内通告。

### 8.4 未来可扩展方向

1. **完整语音配音**：为每个角色配语音，用 Qt Multimedia 播放
2. **CG 立绘系统**：关键剧情节点触发全屏 CG（美术资源可继续扩展）
3. **背景音乐 / 音效**：`assets/audio/bgm/` 和 `sfx/` 目录已预留，可补充素材
4. **移动端适配**：Qt 6 对 iOS / Android 有初步支持，可探索
5. **更多角色路线**：如"数据结构学姐"、"概率论老师"
6. **多结局分支剧本细化**：End2 / End3 按具体主线角色分成 4 个变体

### 8.5 团队协作反思

- **文件归属明确**是三人协作最有价值的约定，减少了 90% 的合并冲突
- **JSON 数据驱动**让剧本作者代易瓒无需等待代码完成即可开始工作，节省了 2 周的关键路径
- **PR review 集中在高风险改动**——纯剧本 / 文档 PR self-merge 更高效
- **文档比对话更可靠**——`docs/接口约定.md` 起到了三方共识锚点的作用
- **联调 buffer 要留够**：最后一周集中打磨了跨模块联动的健壮性，保证 5 结局全部可正常触发
